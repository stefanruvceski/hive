# 07 — Data & State

**Scope:** Local data (expo-sqlite + Drizzle ORM — the primary data path), TanStack Query v5 as the cache over it, the remote `api<T>()` client (secondary, for future integrations), client state, forms, persistence, offline, and Expo Router API route mechanics in Hive. Background: [ADR 0001](../decisions/0001-modules-sqlite-native-only.md).

## Non-negotiables

- [ ] User data lives on the device in one SQLite database (`hive.db`), read and written through Drizzle via `getDb()` from [src/lib/db/client.ts](../../src/lib/db/client.ts) — only inside query/mutation hooks (a module's `data/queries.ts`, a shell screen's `use-<thing>.ts`, or — for app-wide data that the root layout and several screens read, such as Settings preferences — a hook in `src/hooks/`, e.g. [use-app-settings.ts](../../src/hooks/use-app-settings.ts)). Components never call `getDb()`, and nothing loads data in `useEffect`.
- [ ] Schema changes: edit the Drizzle schema, run `pnpm db:generate`, commit the generated migration. Never hand-edit `src/lib/db/migrations/` (§8).
- [ ] Module tables are prefixed with the module id in snake_case (`habits_entries`); core tables live in [src/lib/db/schema.ts](../../src/lib/db/schema.ts).
- [ ] Every domain has a hierarchical key factory + shared `queryOptions` next to its hook — copy [src/screens/home/use-home-layout.ts](../../src/screens/home/use-home-layout.ts) (local) or [src/screens/settings/use-health.ts](../../src/screens/settings/use-health.ts) (remote). Keys include every `queryFn` dependency (lint).
- [ ] Remote HTTP uses `api<T>()` with an explicit response type; errors are `ApiError`. `fetch` outside [src/lib/api.ts](../../src/lib/api.ts) and `src/app/api/**` (lint); `api<any>` (lint).
- [ ] Global query defaults live only in [src/lib/query-client.ts](../../src/lib/query-client.ts) (`networkMode: 'always'`, local-first); override per query, never globally for one screen.
- [ ] Client state: React state → context → Zustand (only in `src/store/`, only under §6 conditions). Redux/MobX/Jotai/Recoil are banned.
- [ ] Tokens on-device go in `expo-secure-store` only (not installed yet); secrets never in `EXPO_PUBLIC_*` and never in SQLite ([13](13-security.md)).
- [ ] Client code never imports `src/app/api/` files (lint for screens/components/hooks/lib; manual check inside `src/app/`).

## 1. TanStack Query v5 — queries

### Key factory + `queryOptions` next to the hook

Module hooks live in `src/modules/<id>/data/queries.ts`; shell-screen hooks live in the screen folder as `use-<thing>.ts`; app-wide data hooks that the root layout or several screens read (Settings preferences: `use-app-settings.ts`) live in `src/hooks/`; shared infrastructure hooks go in `src/lib/` ([01 §2](01-architecture.md)). Every key for a domain comes from one factory (module keys start with the module id), generic → specific, so partial invalidation (`todoKeys.all`) catches all descendants. Each query is defined once with `queryOptions()` and reused by `useQuery`, `prefetchQuery`, `setQueryData`, and tests (prefer-query-options is lint).

```ts
// ✅ CORRECT — src/modules/habits/data/queries.ts (shape generated by pnpm new:module)
export const habitsKeys = {
  all: ['habits'] as const,
  lists: () => [...habitsKeys.all, 'list'] as const,
  detail: (id: string) => [...habitsKeys.all, 'detail', id] as const,
};

export const habitQuery = (id: string) =>
  queryOptions({
    queryKey: habitsKeys.detail(id),
    queryFn: async () =>
      getDb().select().from(habitsEntries).where(eq(habitsEntries.id, id)).get() ?? null,
  });

export function useHabit(id: string) {
  return useQuery(habitQuery(id));
}
```

```ts
// ❌ WRONG — ad-hoc string key outside the factory; breaks partial invalidation
useQuery({ queryKey: ['todoList' + filter], queryFn: () => fetchTodos(filter) });
```

- Changing parameters (filter, sort, id) go in state **and** in the key; never `refetch(newParams)` — `refetch` reuses the same key.
- The Drizzle expo driver is synchronous; wrap calls in an `async` `queryFn`/`mutationFn` so errors become query errors. Return `null` (not `undefined`) for "not found" — TanStack Query rejects `undefined` data.
- Remote queries pass the `queryFn` `signal` through to `api<T>()` (as `use-health.ts` does) so out-of-date requests abort.
- Never store query results in `useState`/context/Zustand "to share them" — call the same hook again; the cache is the shared store.

### Defaults and overrides

[src/lib/query-client.ts](../../src/lib/query-client.ts) sets `networkMode: 'always'` for queries and mutations (§9), `staleTime: 60_000` and a `retry` predicate (`shouldRetryQuery`) that retries network, 5xx, 408 and 429 failures up to 2 times and never other 4xx `ApiError`s. Retry policy and global error handlers are owned by [14 §2](14-errors-resilience.md).

- Override `staleTime` per query in its `queryOptions` (longer for reference data). Never set `gcTime: 0` to "fix" stale UI — fix the key or invalidation.
- v5 renames agents get wrong: `cacheTime` → `gcTime`; initial load is `isPending` (`isLoading` = `isPending && isFetching`); `onSuccess`/`onError`/`onSettled` no longer exist on `useQuery`; `useInfiniteQuery` requires `initialPageParam`.

### Screen states

Every consuming screen renders loading / error / empty / success explicitly (`LoadingState`, `ErrorState` wired to `refetch`, `EmptyState`). UX and copy rules: [14 §3](14-errors-resilience.md).

- **Check `data` before `error`.** A failed _background_ refetch keeps cached `data` with `status: 'error'`; a screen already showing data must keep showing it (optionally with an inline "refresh failed" hint), not swap to a full error screen.
- For local queries, "error" means the database failed — show `ErrorState` with retry. For remote ones narrow `error instanceof ApiError` for status-specific UI; 401/403 → sign-in flow, not a generic error card.
- Use `isPending` for the initial skeleton, `isFetching && !isPending` for background refresh, `isPaused` for offline hints (remote `'online'` queries only).

### Other patterns

- **Dependent queries:** gate with `enabled: !!user?.id` — never effect- or `await`-chained queries. Prefer one SQL query (join) / one endpoint or parallel queries over waterfalls.
- **`select`:** for slices/derived data; prefer a module-level function, no throwing (validation belongs in `queryFn`). No hand-written `useCallback` ([11 §11](11-typescript-style.md)).
- **Seeding:** `initialData` from another query MUST set `initialDataUpdatedAt` (e.g. the list query's `dataUpdatedAt`), else `staleTime` suppresses the refetch. Use `placeholderData` when the seed is partial.
- **Prefetch** on press-in with the same `queryOptions` (`void queryClient.prefetchQuery(todoQuery(id))`); never block navigation on it.
- **Infinite lists:** own key segment (never share a key with a `useQuery`); guard `hasNextPage && !isFetching && fetchNextPage()`; `isFetchingNextPage` for the footer; `maxPages` for long feeds; keep the `{ pages, pageParams }` shape in `setQueryData`.

## 2. Mutations, invalidation, optimistic updates

```ts
export function useCreateHabit() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (input: NewHabit) => {
      getDb().insert(habitsEntries).values(input).run();
    },
    // returned promise keeps the mutation pending until the refetch completes
    onSettled: () => queryClient.invalidateQueries({ queryKey: habitsKeys.lists() }),
  });
}
```

- Naming `useCreateThing` / `useUpdateThing` / `useDeleteThing`; same placement as query hooks. One variables argument — bundle values in an object.
- MUST invalidate (or `setQueryData`) every affected key via the factory hierarchy. Prefer invalidation unless the write returns the complete updated entity. Multi-statement writes run in one `getDb().transaction((tx) => …)`.
- **Callback placement:** cache work (invalidate, writes, rollback) in the hook's `useMutation` callbacks; UI effects (navigation, toasts) in the call-site `mutate(vars, { onSuccess })`, which don't fire after unmount.
- Prefer `mutate`. `mutateAsync` only for promise-shaped needs (`Promise.all`, sequential mutations) and always inside `try/catch`.
- **Optimistic updates** for instant-feedback actions (toggles, reorders) — local writes rarely fail, so they suit SQLite well; reference: `useSetAppSetting` in [use-app-settings.ts](../../src/hooks/use-app-settings.ts). One consumer → render `variables` while `isPending`. Several screens → cache pattern: `onMutate` must `cancelQueries`, snapshot, `setQueryData`, return the snapshot; `onError` restores; `onSettled` invalidates. Submit-and-close/redirect forms use `isPending` on the button instead.

## 3. API client (remote — secondary)

No feature uses a remote backend yet; `api<T>()`, `env.ts` and `src/app/api/health+api.ts` remain for future integrations (sync, imports).

- ALWAYS `api<T>(path, init?)` from [src/lib/api.ts](../../src/lib/api.ts): rejects with `ApiNotConfiguredError` (never retried) when no API URL is set, otherwise prefixes `env.apiUrl`, sets JSON headers, applies a default 15 s timeout unless you pass a `signal`, throws `ApiError(status, message)` on non-2xx. Enforced by lint (`no-restricted-globals` fetch outside `api.ts` and `src/app/api/**`) — no exceptions in client code.
- Remote-only UI renders only when `isApiConfigured()` is true (copy `ServerRow` in `src/screens/settings/components/app-info-card.tsx`); the app must work fully without an API URL.
- Error normalization happens only in `api.ts`; don't re-wrap `ApiError` in hooks — let it reach the query/mutation `error`.
- Cross-cutting concerns (auth header, tracing) go in `api.ts`, not at call sites ([src/lib/AGENTS.md](../../src/lib/AGENTS.md)). No ad-hoc retry loops ([14 §2](14-errors-resilience.md)).

## 4. Server state vs client state

| Kind         | Definition                                                  | Tool                                            |
| ------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| Local data   | User data persisted on the device (habits, entries, layout) | SQLite via Drizzle, read through TanStack Query |
| Server state | Anything persisted remotely (future integrations)           | TanStack Query + `api<T>()`                     |
| Client state | UI-only, ephemeral (modal open, draft input, edit mode)     | React state → context → Zustand                 |

- NEVER mirror persisted or server data into client state, and NEVER put client-only state in the query cache as fake queries. Anything that must survive a restart is a table, not a store.

## 5. React context rules

- Context is for low-frequency, app-scoped data (session, theme, locale); split providers by concern and change frequency, and split state from dispatch when consumers need one. High-frequency shared client state → Zustand (§6).
- Provider values are memoized by the React Compiler — no hand-written `useMemo` (lint). If a provider still churns, fix the Rules-of-React violation that made the compiler skip it ([11 §11](11-typescript-style.md)).

## 6. When Zustand is justified

Only when all hold: the state is client-only, used by 3+ unrelated screens/components, and context would cause measurable churn. Then:

- One store per file in `src/store/`, named `use<Thing>Store` (file `use-<thing>-store.ts`). Install with `pnpm add zustand` (pure JS).
- Small, flat stores with actions inside; components select narrow slices (`useCartStore((s) => s.items.length)`), never the whole store.
- Never persisted data, server data or tokens in a store.

## 7. Form state

- Drafts are local `useState`/`useReducer` in the screen — not context, Zustand, or the query cache.
- Submission is a mutation hook: `isPending` disables submit, `isError` shows inline errors, `reset()` on cancel.
- A form library needs a proposal in the PR first; don't add one unilaterally.
- Validate in the mutation (or the module's `domain/` logic) before writing to SQLite; for remote writes the API route/server is the boundary and client-side validation is UX only ([13 §7](13-security.md)).

## 8. Persistence — SQLite + Drizzle

- **One database:** `hive.db`, opened lazily by `getDb()` in [src/lib/db/client.ts](../../src/lib/db/client.ts) — never at import time ([review-lessons L-001](review-lessons.md)). Don't open other databases.
- **Schema:** core tables in [src/lib/db/schema.ts](../../src/lib/db/schema.ts) (e.g. `home_groups`, `home_apps`, `settings`); module tables in `src/modules/<id>/data/schema.ts`, every name prefixed `<id_snake>_`. A module only reads/writes its own tables.
- **Migrations:** [drizzle.config.ts](../../drizzle.config.ts) collects all schema files; `pnpm db:generate` (drizzle-kit) writes SQL + `migrations.js` to `src/lib/db/migrations/`. Generated, lint/prettier-ignored, committed, never hand-edited; review the SQL before committing. A destructive change (drop/rename column) needs a data-preserving migration — say so in the PR.
- **Applying:** the root layout runs `useMigrations(getDb(), migrations)` and keeps the splash up until done; a migration error throws to the root ErrorBoundary ([14 §1](14-errors-resilience.md)). `babel.config.js` (inline-import for `.sql`) and `metro.config.js` (`sql` source extension) make the migrations bundleable — don't remove them.
- **Tests:** expo-sqlite has no JS implementation in Jest — mock the data hooks and test pure logic directly ([09 §5](09-testing.md)).

| Data                                    | Storage                                   | Status                                              |
| --------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| User data, structured/queryable records | `expo-sqlite` + `drizzle-orm` (`hive.db`) | Installed — **primary**                             |
| Tokens, refresh tokens, anything secret | `expo-secure-store` (Keychain/Keystore)   | Not installed: `npx expo install expo-secure-store` |
| Small non-sensitive preferences         | a core table in `src/lib/db/schema.ts`    | Prefer SQLite over adding AsyncStorage              |

- A new storage library is a native dependency → [08 §4](08-native-config.md) and a store release.
- What counts as sensitive and where tokens live (memory vs SecureStore): [13 §2](13-security.md).

## 9. Offline considerations

- Hive is local-first: SQLite works offline, so the query client uses `networkMode: 'always'` for queries and mutations — local reads and writes never pause.
- Remote queries/mutations opt back in with `networkMode: 'online'` in their own `queryOptions`/`useMutation`, so offline they go `paused` (not `error`) and resume on reconnect — surface `isPaused`, don't invent offline detection.
- Remote sync (`onlineManager` + `@react-native-community/netinfo`, queued paused mutations) is opt-in and must be proposed first; netinfo is a native dep.

## 10. Expo Router API routes (`src/app/api/*+api.ts`)

Placement, input validation and the error shape: [src/app/AGENTS.md](../../src/app/AGENTS.md); authz: [13 §8](13-security.md); error contracts: [14 §7](14-errors-resilience.md).

- Handlers are named after HTTP methods (`GET`, `POST`, …), signature `(request: Request, params: Record<string, string>)`; unsupported methods return 405, thrown errors 500. Body via `await request.json()`, query via `new URL(request.url).searchParams`.
- Server-only secrets use non-`EXPO_PUBLIC_` names and are read only in `+api.ts` files (or modules imported solely by them); Metro keeps them out of the client bundle only under that condition. `src/app/api/**` is the only place exempt from the `process.env`/`fetch` lint bans.
- No platform extensions in route filenames (`hello+api.web.ts` is invalid).
- Clients call routes through a query hook with `api<T>('/api/...')` (see `src/screens/settings/use-health.ts`), which resolves against `env.apiUrl` — so routes must be deployed at that origin for native builds.

```ts
// ✅ CORRECT — src/app/api/things/[id]+api.ts
export async function GET(request: Request, { id }: Record<string, string>) {
  if (!id) {
    return Response.json({ error: { code: 'not_found', message: 'Not found' } }, { status: 404 });
  }
  return Response.json(await loadThing(id, process.env.THINGS_API_KEY)); // server-only secret
}
```

## Common agent mistakes

1. Inventing ad-hoc keys instead of extending the domain's key factory — breaks partial invalidation.
2. Copying query data into state/context/Zustand "for sharing" instead of calling the same hook.
3. Calling `refetch(newParams)` instead of putting the value in state and the key.
4. Forgetting to invalidate after a mutation, or invalidating too narrow a key.
5. Cache-optimistic updates without `cancelQueries` + snapshot/rollback.
6. v4 names: `cacheTime`, `isLoading` for initial load, `onSuccess` on `useQuery`.
7. Replacing a rendered screen with a full error state when a background refetch fails.
8. `initialData` seeded from another query without `initialDataUpdatedAt`.
9. Navigation/toasts in the hook's `onSuccess` instead of the call-site callback; `mutateAsync` without `try/catch`.
10. Importing helpers from a `+api.ts` file into client code — leaks server code and secrets into the bundle.
11. Calling `getDb()` in a component or at module scope, hand-editing a migration, or a module table without the module prefix.
